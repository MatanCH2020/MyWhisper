# ניהול הורדות ותקלות — MyWhisper

מערכת הניהול היא פרויקט Studio נפרד ב־Sticklight, עם מסד נתונים והרשאות שרת.
האתר הציבורי והתמלול המקומי אינם תלויים בזמינות מערכת הניהול.

## מה המדדים אומרים

- הורדת `MyWhisper-Setup.cmd` נספרת כ־Windows; חבילת `MyWhisper-X.Y.Z[bN]-macos-arm64.dmg` כ־Mac.
- קובצי בדיקת תקינות, מדריכים, ארכיוני מקור וגרסאות טיוטה אינם נספרים.
- מדובר בהורדות קבצים, כולל בדיקות והורדות חוזרות. זו אינה ספירת משתמשים או התקנות מוצלחות.
- התקנה בפקודת PowerShell אינה מורידה את קובץ המתקין ולכן אינה נכללת במדד הזה.
- המדידה הראשונה היא נקודת התחלה מצטברת. אין שחזור בדיעבד של הורדות לפי יום.
- זמני האיסוף נשמרים ב־UTC ומוצגים לפי שעון ישראל. פערים באיסוף ושינוי במזהה נכס אינם גידול רגיל.

## איסוף ושמירה

GitHub Actions מפעיל את `.github/workflows/download-metrics.yml` מדי שעה ובאופן ידני.
הזמנים אינם התחייבות: GitHub עשוי לעכב משימות מתוזמנות. לוח הניהול חייב להציג זמן עדכון אחרון.
המשתנה הציבורי `MYWHISPER_METRICS_URL` מצביע לפונקציית `sync-downloads`.

לצורך האימות נבחר GitHub Actions OIDC במקום מפתח משותף. האסימון הקצר נוצר בזמן
המשימה, נשלח רק לפונקציית השרת ואינו נשמר בקוד או מוצג בלוגים. השרת מאמת חתימה,
מנפיק, קהל `mywhisper-download-sync`, תוקף, המאגר `MatanCH2020/MyWhisper`, הענף `main`,
קובץ ה־workflow המדויק וסוג האירוע. רק `schedule` ו־`workflow_dispatch` מותרים.

השרת קורא את כל עמודי GitHub ושומר מדידה שלמה בלבד. כשל אינו מוחק או מאפס נתונים קודמים.
רענון ידני דרך הממשק דורש מנהל מאומת. אין מפתח ניהול בתוכנת המחשב.

## דיווח מתוך התוכנה

בהגדרות בוחרים **דיווח על תקלה**, מתארים את הבעיה, ובודקים את הנתונים הטכניים לפני **שלח דיווח**.
פרטי קשר הם לבחירה. בדקו שלא הוספתם מידע אישי לתיאור החופשי.

מצורפים רק פרטים טכניים מוגדרים: גרסת התוכנה ומערכת ההפעלה, ארכיטקטורה,
גרסאות Python/Qt, מנוע ומודל מוכרים, GPU/CPU ומדדי אבחון מספריים זמינים.
אין קריאה של קובצי היסטוריה, לוח, מילון, פרטי חשבון, הקלטות או לוגים גולמיים.
פתיחת הטופס אינה שולחת דבר. אין דיווח אוטומטי או מעקב שימוש.

השליחה היא בקשת HTTPS יחידה, ללא הפניה אוטומטית לכתובת אחרת וללא ניסיונות רקע.
הטופס נשאר פתוח בכשל; ניסיון חוזר של אותו תוכן משתמש באותו מזהה למניעת כפילות.
שינוי התוכן יוצר מזהה חדש. מספר דיווח מוצג רק לאחר תשובת שרת המאשרת שמירה.

ממשק `submit-report` מקבל JSON בגרסה 1: `request_id`, `category`, `description`,
`contact`, `diagnostics` ו־`schema_version`. הוא מאפשר כתיבה בלבד, עם הגבלת גודל וקצב.
אישור שמירה הוא HTTP 200/201 עם `ok: true` ו־`report_id`. אין API ציבורי לקריאת דיווחים.

## הרשאות ותפעול

- התחברות Google כשלעצמה אינה מעניקה ניהול. טבלת `app_admins` מתחילה ריקה.
- יש להעניק מנהל רק דרך מסלול ניהול מהימן, לחשבון בעל הפרויקט שאומת ב־Google;
  לעולם לא לפי „הנרשם הראשון” או כתובת שהדפדפן מספק.
- קריאה, ייצוא, הערות, שינוי סטטוס ומחיקה מוגנים בשרת וב־RLS. גם משתמש מחובר שאינו מנהל חסום.
- להגשת דיווח אין צורך בחשבון. אסור לחשוף `service_role` או סודות אימות בתוכנה או בדפדפן.
- אפשר לסמן דיווח חדש/בטיפול/תוקן/נסגר, לציין גרסת תיקון ולהוסיף הערות פנימיות.
- דיווחים הם מדגם יזום: אין להסיק מהם שיעור תקלות אצל כלל המשתמשים או דיוק תמלול.

## בדיקות לפני הפעלה

1. להריץ `python -m unittest tests.test_support tests.test_download_metrics tests.test_ui_pages` מתוך ה־venv.
2. לשלוח דיווח סינתטי, לחזור על אותו מזהה ולאמת אותו מספר, ולוודא ששינוי מטען עם אותו מזהה נדחה.
3. לבדוק דחיית נתונים לא מוכרים, גודל עודף וקצב מוגזם; לוודא שאורח וחשבון שאינו מנהל אינם קוראים נתונים.
4. להפעיל ידנית את workflow האיסוף ולקרוא בחזרה מדידה שמורה; הצלחת HTTP בלבד אינה הוכחת שמירה.
5. לבדוק את מסך הדיווח ב־Windows ואת אתר הניהול במחשב ובמובייל, עם נתוני בדיקה בלבד.
6. לפני הכרזת השלמה לאמת התחברות בעלים, הרשאת מנהל, CI, פריסה, גרסאות והורדות.
